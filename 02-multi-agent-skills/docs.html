Multi-Agent Skills Demo

Build Kubernetes-native AI agents with skills, register them in a catalog, route all LLM traffic through a governed proxy, and evaluate agent behavior with OTel traces — all in a local kind cluster.

kagent agentgateway agentregistry agentevals

The Story

Team A (SRE) captures their Kubernetes expertise as portable, versioned skills. They build two specialist agents — one for deployment, one for health diagnostics — and register them in a shared catalog.

Team B (Platform Engineering) searches the catalog, discovers what Team A built, and composes a multi-agent incident response system without writing a single kubectl command. The specialists become tools in a coordinator agent.

All LLM traffic flows through agentgateway. All agent behavior is traced via OTel and scored with agentevals. Two teams. Shared skills. Full-stack governance.

Four open-source components, all running in a single kind cluster. No external dependencies beyond an OpenAI API key.

LLM Traffic Flow

Every LLM call from every agent flows through agentgateway. No agent pod has direct access to the OpenAI API key. The gateway holds the credentials and proxies all requests.

Three Kubernetes resources make this work

ResourceKindPurpose
ai-gateway Gateway Creates the proxy listener on port 80, standard Kubernetes Gateway API
openai HTTPRoute Routes /openai path prefix to the OpenAI backend
openai AgentgatewayBackend Defines OpenAI as an LLM provider, authenticates via openai-secret

The ModelConfig patch

After installing kagent, the install script patches the default-model-config to route through the gateway instead of calling OpenAI directly: 

kubectl patch modelconfig default-model-config -n kagent \
  --type merge \
  -p '{"spec":{"baseUrl":"http://ai-gateway.agentgateway-system.svc:80/openai/v1"}}'

All three agents reference modelConfig: default-model-config, so this single patch routes every LLM call through the gateway. The agents never see the OpenAI API key — the gateway injects it from a Kubernetes Secret.

ℹ
Security benefit: The OpenAI API key lives only in the agentgateway-system namespace. Agent pods in the kagent namespace have zero access to it. Credential rotation happens in one place.

The 3 Agents

k8s-deploy-agent

TEAM A · 6 MCP Tools · Read/Write

Validates manifests with dry-run, applies changes, monitors rollouts, handles rollback on failure.

Tools: k8s_apply_manifest, k8s_get_resources, k8s_get_events, k8s_get_pod_logs, k8s_describe_resource, k8s_delete_resource

k8s-healthcheck-agent

TEAM A · 5 MCP Tools · Read-Only

Diagnoses workload health with structured reports and actionable remediation steps.

Tools: k8s_get_resources, k8s_describe_resource, k8s_get_resource_yaml, k8s_get_events, k8s_get_pod_logs

incident-response-agent

TEAM B · 2 Sub-Agents · Orchestrator

Coordinates incident response by delegating to specialist agents, correlating findings, and producing summaries.

Tools: k8s-deploy-agent (agent-as-tool), k8s-healthcheck-agent (agent-as-tool)

Agent-as-Tool pattern

The incident-response-agent uses type: Agent in its tool spec, which turns the specialist agents into callable tools:

tools:
  - type: Agent
    agent:
      name: k8s-deploy-agent
  - type: Agent
    agent:
      name: k8s-healthcheck-agent

Team B never writes a single kubectl command. They compose existing capabilities from the catalog.

Skills & Composition

A skill is a structured document that captures operational expertise: what tools to use, in what order, what to look for, and how to format the output. Skills are embedded as system messages in agent CRDs.

What makes a skill?

  • Tools — which MCP tools the agent has access to
  • Procedure — the ordered sequence of steps (e.g., "check pods first, then events, then logs")
  • Error handling — what to do when things go wrong
  • Output format — structured, consistent reporting

Skill Registry

agentregistry is a catalog for AI artifacts — skills, agents, and MCP servers. Teams register what they build, and other teams search and discover it. Like Artifact Hub, but for AI.

OTel Tracing & Evals

Every agent call generates OTel traces that flow to agentevals. One Helm value enables it — the same OTLP protocol used for microservices. 

# Set during kagent Helm install
otel.tracing.enabled=true
otel.tracing.exporter.otlp.endpoint=http://agentevals.default.svc.cluster.local:4318/v1/traces
otel.tracing.exporter.otlp.protocol=http/protobuf

What gets traced

  • Every LLM call (model, prompt, response)
  • Every tool invocation (tool name, arguments, result)
  • Every agent-to-agent call (delegation chain)
  • Full span tree for multi-agent workflows

Evaluation scoring

MetricWhat it checks
tool_trajectory_avg_scoreDid the agent call the right tools in the right order?
response_match_scoreDoes the final answer match expected output?
hallucinations_v1Did the agent fabricate information not in tool responses?
✔
Golden path scoring: Record a good run as the golden path, then score every future run against it. If the healthcheck agent skips the event check, trajectory scoring catches it instantly: "Expected 3 tools, got 2. Score: 0.66. FAIL."
